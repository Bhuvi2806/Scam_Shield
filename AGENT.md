# AGENT.md: Scam Shield

This file is the rulebook for any AI agent working on this repository.
**Rule 0: At the start of EVERY task, read this whole file first, then follow it.** If a user instruction conflicts with a rule below, the user's latest explicit instruction wins, except for the Hard Stops in section 3.

---

## 1. Project Context

**Scam Shield** is a web app where a user pastes a suspicious SMS / WhatsApp message / call transcript, or uploads a screenshot, and gets:
- a verdict: `Safe` / `Suspicious` / `Likely Scam`, with a confidence score
- highlighted red flags inside the message
- a plain Hindi/English explanation of *why*
- a "what to do now" checklist (1930 helpline, cybercrime.gov.in)
- a WhatsApp-shareable "Family Mode" card

**Stack:** React + Tailwind (mobile-first) | FastAPI (Python 3.10+) | Tesseract / EasyOCR (Hindi + English) | Claude API (classification + explanation) | Google Safe Browsing API (URL check)

**Architecture:** Input Handler -> (OCR if image) -> Rule Detector + URL Checker + LLM Analyzer -> Score Fusion -> Dashboard output.

**Suggested layout**
```

  backend/   app/{api,core,detectors,llm,ocr,schemas}  tests/  data/
  frontend/  src/{components,pages,hooks,lib}
```

## 2. Autonomy Rules (permission override)

The user has pre-approved autonomous work. Therefore:

1. **Do not ask for permission** for routine actions: creating/editing/renaming files, installing project dependencies, running tests/linters/dev servers, creating folders, refactoring inside the project, committing to a feature branch.
2. **Do not stop to ask "should I continue?"** between phases. Finish all phases of the task, then report.
3. **Make reasonable decisions yourself** when something is ambiguous. Pick the simplest option that fits this file, record it in `docs/decisions.md` (one line: decision + why), and keep going.
4. **Fix your own errors**: if a test or build fails, debug and retry (up to 3 different approaches) before reporting a blocker.
5. Ask the user only when a Hard Stop (section 3) applies, or when the task is impossible without information only the user has (e.g., an API key).

## 3. Hard Stops (autonomy does NOT cover these)

Stop and ask first if the action would:
- delete data or files outside the project, or run `rm -rf` on anything not generated by you
- force-push, rewrite git history, or push to `main` directly
- commit or print **secrets** (API keys, `.env` contents). Keys live only in `.env`, which stays in `.gitignore`
- spend real money (paid API plans, cloud resources) beyond the free tier
- send real user messages or personal data to any third party other than the declared APIs (Claude API, Safe Browsing)
- use real people's phone numbers, names, or bank details in code, tests, or dataset

## 4. Phase-Based Workflow (mandatory for every task)

Divide **every** task into the phases below. Skip a phase only if it truly does not apply, and say so in the log.

| Phase | Name | What to do | Exit check |
|---|---|---|---|
| 0 | **Understand** | Read AGENT.md, `docs/progress.md`, and the relevant code. Restate the task in 2-3 lines. | Task + scope are clear |
| 1 | **Plan** | Break the task into small steps. List files to touch and tests to add. Write the plan at the top of `docs/progress.md`. | Plan written |
| 2 | **Implement** | Work step by step, in small increments. One concern per commit. Follow section 5 rules. | Code runs |
| 3 | **Test** | Add/update tests. Run the full test suite and linters. | All green |
| 4 | **Review** | Re-read your own diff. Remove dead code, check edge cases, check privacy + disclaimer rules (section 5). | Self-review done |
| 5 | **Document & Report** | Update README/docs, update `docs/progress.md`, give the final report (section 7). | Report sent |

**Phase rules**
- Never start the next phase while the current phase's exit check fails.
- Large tasks (a whole feature or milestone) are split into sub-tasks, and each sub-task goes through phases 0-5 on its own.
- Log each phase in `docs/progress.md` with a one-line status: `[Phase 3] tests: 24 passed, 0 failed`.

## 5. Project-Specific Rules

**Privacy**
- Never store submitted messages by default. Process in memory and discard. Any logging must be anonymized (strip numbers, names, URLs) and opt-in.
- Do not log full message text, even in debug mode.

**Safety of output**
- Never output "100% safe". The lowest-risk verdict must carry: *"No red flag found, but never share OTP, PIN or money with anyone who contacts you."*
- When unsure, lean toward `Suspicious`, not `Safe`. A false negative is worse than a false positive here.
- The explanation must name the concrete red flags found (urgency, authority impersonation, OTP/money demand, suspicious link, "stay on video call", etc.), not just say "scam".

**Detection design**
- Keep it hybrid: rule layer + URL check + LLM layer, fused into one score. Never rely on the LLM alone.
- The LLM must return **structured JSON** (verdict, scam_type, red_flags[], explanation_en, explanation_hi, confidence). Validate it with a schema; on invalid output, retry once, then fall back to rule-only result.
- Supported scam types: digital arrest, fake KYC, UPI refund, job/task scam, lottery/prize, electricity-bill threat, other.
- If the LLM API fails or times out, the app must still return a rule-based verdict, never a crash.

**Language and UX**
- Every user-facing explanation is available in Hindi and English, in simple words an elderly person can follow.
- Mobile-first, accessible UI: sufficient contrast, labels on inputs, keyboard navigable, readable font sizes.
- Always show the "what to do now" checklist with 1930 and cybercrime.gov.in.

**Code quality**
- Backend: type hints, Pydantic schemas, small functions, `pytest` tests. Format with `ruff`/`black`.
- Frontend: functional components, no unused dependencies, `eslint` clean.
- No hard-coded secrets, URLs or magic numbers; use config/`.env` and constants.
- Detector rules live in data files (`backend/data/patterns.json`), not buried in code, so they can be extended without code changes.

**Testing and evaluation**
- Maintain a labelled test set `backend/data/test_set.json` (scam vs genuine bank/service messages, Hindi + English). Use only synthetic or public-awareness examples.
- Every detector change must be re-run against this set; report accuracy, false positives and false negatives in `docs/progress.md`.
- Include tricky genuine messages (real bank OTP alerts, delivery updates) so the tool does not over-flag.

## 6. Git Rules

- Work on a branch named `feat/<short-name>` or `fix/<short-name>`. Never commit directly to `main`.
- Commit messages: `type: short summary` (`feat`, `fix`, `test`, `docs`, `refactor`).
- Commit after each completed step, not one giant commit at the end.

---

## 7. Final Report Format

When a task finishes, reply with only:
1. **Done:** what was built or changed (2-4 lines)
2. **Tests:** what was run and the result
3. **Decisions:** any choices you made on the user's behalf
4. **Blockers / needs from user:** only if any (e.g., missing API key)
5. **Next step:** one suggested follow-up

Keep it short. Do not narrate every step.
